# 游玩性能调查 — 2026-10-22

本轮按用户最新要求仅测试、分析，不实装帧数选项或性能修改，不提交 Git。用户常用 NOTE SPEED 为 5；收到“流速差不多就行了”后停止逐档穷举，保留代表档位测试。

## 结论

- **流速 5 的明显持续卡顿未复现，但不能据此宣称问题解决。** Sunlight 首次进入、同曲重开及寄明月各观察开头 45 秒，总计 135 秒。大多数浏览器刷新回调间隔为 8.3ms；音符位置／媒体时钟大多数约 16.7ms 更新一次。存在少量 33～50ms 更新间隔，没有超过 50ms 的主线程长任务。
- **音符目前有约 60Hz 更新限制。** 这与测试窗口实测约 120Hz 的浏览器刷新回调不同。流速越高，每次更新的位移越大，可能更容易看出步进感；这不是已经证实的偶发卡顿根因。本轮没有解除限制，也没有做 60/120Hz 音符更新的对照实验。
- 流速 8、10 的开头 18 秒没有明显性能恶化。提高流速不等于增加同屏音符数量，当前实现反而会缩短预览区间。
- **另有一项低流速异常：0.5 档的一次测试明显掉帧。** 浏览器回调平均约 55Hz，视频报告丢弃 748/1005 帧，媒体时钟更新最大间隔 325ms；没有对应的主线程长任务。该异常只测到一次，未做重复或 GPU trace 定位，不能直接归因于缓存、视频解码或某个滤镜，也不能用来解释用户流速 5 的问题。

## 测试条件与方法

- 当前工作区正式构建，构建成功；测试服务器使用 Vite **preview**，不是 Vite 开发服务器。保存基线入口及 JS/CSS，避免混入不同构建。未修改现有功能代码。
- Windows，Chrome 独立临时配置，2560×1440 内容视口，有窗口、GPU 开启；RTX 4060 Laptop GPU。媒体事件记录实际使用 `D3D11VideoDecoder`，平台视频解码启用。
- 系统显示信息为 2560×1600、165Hz，但本轮正常样本的 RAF 实测约 120Hz。不能将本轮结果当作真实 165Hz 呈现验证。
- 使用真实 maps 中的已发布谱面和视频：Sunlight 实测 1920×1080，寄明月实测 2560×1440，正常播放速率 1。通过原有选曲、准备、倒计时进入游玩；流速通过隔离浏览器的设置界面调整。
- 复制 maps 元数据到隔离目录，视频只建临时硬链接，不复制视频内容。未连接个人浏览器资料，也未清空个人站点数据。
- 采集 RAF 间隔、媒体时钟更新、同一 TAP 的位置变化、视频丢帧计数、Long Task、Long Animation Frame、资源加载及 CDP 指标。截图仅在计时停止并暂停视频后执行。
- RAF 表示浏览器回调机会，**不等于每次都实际显示了新画面**；视频丢帧为浏览器 `VideoPlaybackQuality` 计数。音符位置采样只跟踪选定 TAP，并非所有 HOLD/SWAY 的逐帧验证。

## 代码证据与解释范围

- `src/media.ts` 的 `MediaController.tick` 使用 `1000 / 60` 限制时间发布；读取真实 `video.currentTime`。原生 `timeupdate` 也会发布时间，因此实际订阅更新数可能略高于每秒 60 次。`src/media.test.ts` 明确验证 60/120/144/240Hz 下最多约 60 次 RAF 时间发布。
- `src/views/Player.tsx` 通过 `useTime(media)` 驱动 React／SVG，`previewMs = 3600 * DEFAULT_NOTE_SPEED / noteSpeed`，默认流速常量为 3。流速 5 的预览约 2160ms，0.5 则为 21600ms。
- 按 Sunlight 原始谱面和当前可见时间过滤规则估算，前 18 秒原始同屏事件峰值：0.5 档约 41 个、5 档约 10 个、8/10 档约 8 个。此估算未应用 ARMS 合并，不能当作实际 DOM 节点数。它支持“低流速可能增加渲染负担”的调查方向，不足以证明异常成因。
- `src/components/HoldRibbon.tsx` 已有限制屏外 SVG 范围的处理，长条柔光采用多层透明轮廓，白边仍有 `feMorphology`；`src/practice.css` 的普通音符和部分提示仍使用 `drop-shadow`。不能把当前实现描述成“完全没有柔光／滤镜”。未做滤镜开关对照，不能认定它们就是本轮根因。
- 流速 5 的观测段未发现图像／音符纹理在游玩途中才加载的证据。第二次 Sunlight 有少量现有视频 Range 请求，不能视为缓存漏预热的证明。
- CDP Script/Task/Layout 指标的差值包含进入准备及倒计时，不能除以游玩时长后称为纯游玩 CPU 占用。未以这些数字下根因结论。

## 尚未确认与下一步

1. 用户个人 Chrome 中偶发卡顿与独立测试窗口表现的差异：其他标签页、扩展、窗口状态、GPU／电源负载、实际刷新节奏尚未做同条件比较。不能武断归咎于任何一项。
2. 本轮只覆盖开头 18/45 秒，没有验证完整长曲、所有 SPECIAL、长时间连续游玩、4K 视频或其他设备。
3. 帧数选项可以作为后续任务讨论，但不要直接全局去掉 60Hz 限制：当前限制同时减少 React/SVG 重建成本。应先在用户常用流速 5、相同窗口条件下，比较 60Hz 与跟随刷新率的实际呈现和成本，再决定默认值。
4. 如继续调查低流速 0.5，先重复原场景；复现后抓短时间 GPU／合成／绘制时间线，确认是同屏图形负担、解码还是环境波动，再做单因素对照。用户这次已要求流速测试适可而止，未继续展开。

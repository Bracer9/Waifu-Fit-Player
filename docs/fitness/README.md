## 学习资料与规则

- [积木学习记录](LEARNING.md)：三首来源、SHA256、168 个候选／35 个初版积木、动作循环与镜像规则。
- [音乐关联分析](MUSIC-RELATION.md)：三首音轨与人工编排的重复／镜像对照，包括音乐相似但动作不同的反例。
- [数据化积木库](../../src/fitness/bricks.json)：以拍为单位的完整多轨序列、来源时间、小节、起止姿态、镜像要求、来源出现数和音乐能量分位特征。
- [完整音乐对照数据](music-study.json)：216 组片段配对，不将这些样本内结果当成独立测试准确率。

初版是从参考谱提取的规则／模板生成器，没有训练神经网络，也不分析视频人物动作。常量速度和起点沿用本项目的本地音频算法。通过同一份全曲包络检查分段速度证据，明显变速／歧义时停止生成，保留原谱面；尚不自动生成多段 BPM 谱面。

组合保留原内部配合，不把任意两轨随机叠加。选择考虑核心三轨覆盖、音乐相对能量、已用部位及模板复用；Side Crunch 不参与强制覆盖，改为少量短点缀。运行时去除来源窗口的前置留空，保留恢复空间，仅将完全重复的循环缩为短单元；不对称积木必须成对镜像。蹲起和踮脚周期均回到站立，长条不截断，单次保持不超过15秒。曲速超过180时动作采用半速网格，保留原音乐BPM。

音乐指纹描述起音节奏和相对音量变化，不识别旋律／歌词。v2先比较候选边界前后各两小节的特征，规划乐句，再对实际编排段落比较重复音乐；相似段落提升同一积木的复用优先级，报告记录是否实际复用。没有强变化证据时使用八小节框架；开头不固定等待两小节。段落以完整短循环填齐，不再为候选边界跳过空小节，不能保证自动理解所有音乐结构。

## Fitness 积木工具

打开Fitness草稿，在原右侧属性栏选择「积木」。按动作类别选取，设置组数／左右镜像，点击「插入并前进」或双击卡片；也可拖到时间轴的目标小节。完整保留多轨配合，不覆盖已有动作，不跨变速点、不越过游玩终点；使用原撤销／重做。详细限制和验证见[修订报告](REVISION-2026-10-23.md)。

## 实现与验证

`fitness.worker.ts` 按块读取最长 20 分钟音轨，复用 8 MiB 压缩数据缓存，只保留小型起音／能量包络；不解码视频、不调用 API，不增加游戏常驻计算。失败／取消终止 Worker，任务超时 180 秒。完整分析时长随媒体长度变化，本轮实际曲目约 3.5 秒。

`FitnessGenerateButton.tsx` 复用 ModalBackdrop，提供进度、取消、结果与下载。App 使用既有 maps 写入队列和版本保护存储 Fitness 槽，保留其他槽位；原草稿已有内容时，生成后确认替换。生成不是普通单字段编辑，安装新槽时重置为新草稿的编辑历史；原 managed JSON 仍使用既有 `.wfp-backup` 备份机制。

256 项单测和一键流程浏览器用例通过。浏览器验证真实合成音轨分析／保存、Dance／发布版本保留、拒绝替换及中途取消；新 UI 实际截图已检查。本曲样本使用正式构建 Worker 从真实 MP4 生成，再经既有 MapsWorkspace 保存。原参考谱面和目标 Dance 文件逐字节校验未变，实际写入限于目标 Fitness 文件、目标项目清单及其正常备份／关联曲绘资源。未创建 Git 提交。

本机细节与截图归档在 Git 忽略的 `artifacts/fitness-generator-2026-10-23/`，包括操作前清单、目标备份、正式 Worker 结果和保存核验。不要用离线 mono 快速实验的 `offline-preview.json` 代替最终正式 Worker 的 `production-result.json`，两种解码方式的包络存在差异。

最终校验 81 个原 maps JSON：仅目标曲的 project.json 及其正常备份变化，新增目标 Fitness 草稿，无文件缺失；参考曲目和目标 Dance 原字节不变。正式版在独立复制项目中打开实际 MP4，并抽查 7／68／132／205 秒画面，无页面异常；测试服务及临时浏览器已关闭。

# 第一拍候选检测 — 2026-10-23

## 使用与边界

工作台 → 节拍段 → 核对 BPM → 点击「本段 Offset / ms」右侧的检测按钮。成功后填入当前段起点，可以撤销；已有音符的绝对时间、视频偏移和播放状态不变。该操作沿用已有草稿自动保存流程，因此在自己的谱面上点击会修改该草稿的锚点；本次实验没有在原谱面上点击或保存。

本功能估计节拍网格的起始候选，不是音乐结构／小节强拍分类器。整数拍之差虽然可能仍对齐节奏，却会改变小节编号和强拍标记，不能据此称为与人工起点完全一致。BPM 不准、切分明显、弱起或前奏节奏不稳定时，需要试听手动修正。

## 最小实现

- `src/first-beat.ts`：限定搜索区间，复用三频段起音包络；按当前 BPM 扫描相位，限制孤立大峰的权重，以后续连续节奏支持和相位突出度筛选，再回溯到攻击起点。低可靠度不填入。
- `src/bpm.ts`、`src/bpm.worker.ts`：扩展现有检测消息类型，第一拍任务最多分析 60 秒音频，BPM 仍最多 90 秒；复用有界读取和 8 MiB 缓存，不分析视频画面、不播放音频、不引入 API 或依赖。
- `src/components/BpmDetectButton.tsx`、`src/views/Editor.tsx`：复用原按钮／进度／取消机制，只改当前节拍段锚点。视频时间转换采用原 `chartTimeAt`；换段、换视频、改 BPM／锚点会终止旧任务。

## 后续追查：愛スクリ～ム的 BPM 误判

用户指出检测 BPM 不对后，使用同一正式 Worker 在独立只读页面复现：默认最多 90 秒检测返回 88 BPM、confidence 约 0.314；按 88 检测第一拍失败；只把检测参数改为 132 BPM 后，返回视频 990ms 的第一拍候选、confidence 约 0.597。未将参数或结果写回原 maps。

另外离线解码不同 30 秒片段，复用当前算法：0／15／30 秒开始的片段均返回 88；60 秒开始返回 132.25，90 秒开始返回 131.9。因此约 132 有后续片段的独立支持，但仍未做人耳强拍校准。88 恰为 132 的 2/3；结合当前自相关／拍倍数评分机制，较长的重复节奏胜过真实拍周期是合理解释，不能简单归为倍速／半速问题。

当前 BPM 算法只选择整段相关评分最高者，没有验证多个独立片段的速度一致性，也未比较这些候选是否支持稳定的起始网格；其相关强度不是「BPM 正确的概率」。第一拍算法随后使用错误的 BPM 搜索，最终因缺少稳定支持拒绝填入。此曲的前次失败不能仅归因于「节奏证据不足」，上游 BPM 误判是已复现的关键原因。该轮仅诊断并补充记录，尚未修改 BPM 算法。

证据：本机 `icecream-diagnosis.json` 与 `icecream-production-diagnosis.json`，位于上述 artifacts 目录。临时浏览器与随机端口服务已关闭。

## BPM 改进与变速保护（后续实现）

本节替代上节「尚未修改」的状态。用户随后授权改善算法，并询问中途提速／降速支持。

`bpm.ts` 现在保留最多六个有相关支持且相互分离的速度候选，比较各自能否形成相位清晰的拍点网格，以有限幅度重排原评分。既不按歌曲名称特判，也不将所有慢速结果硬翻倍。首次提高网格权重的试验使合成 75 BPM 被误选为 150，随后降低重排幅度；既有 75／90／120／148／174／196 及带噪声用例均保持通过。

新增 `analyzeTempo`：复用同一份包络，不再读取或解码另一遍音频；按 12 秒窗口、末窗至少 8 秒，比较速度证据。短窗的近似候选参考整段支持，避免仅凭重拍方式改变就误报变速；弱证据的半／倍速读法合并，强而持续的分歧仍会提示。显著不一致时 Worker 返回「可能变速或节奏歧义，请分节拍段后检测，原 BPM 未修改」，沿用失败不填入的界面路径。

**变速支持的实际边界**：谱面已有的多个 tempoSegments 可以表达各段不同 BPM，本次没有改变这个数据模型。检测只检查当前段起点后的最多 90 秒，不是全曲扫描，不自动定位变速时刻，也不自动插入或修改节拍段。建议在已知变速处手动添加段，再分别检测。短于窗口的短暂变化、小于约 4% 的变化、证据弱的渐变及半／倍速歧义可能漏检；提示「不一致」也不能当作已经证明真实变速。第一拍检测仍使用当前段固定 BPM，不是变速跟踪器。

浏览器测试的新谱面使用随机视频名隔离，避免多个测试共同使用同名本地作品触发磁盘版本冲突；磁盘防覆盖保护本身保持不变。

本轮最终 4 项 BPM／第一拍浏览器测试全部通过，测试服务已自动关闭。对原 maps 的操作仍限只读。再次与前一任务开始时的 69 文件快照比较，发现 9 个文件内容变化及 5 个新增、无缺失；快照跨越用户后续操作，不能据此宣称本轮结束时原目录与旧快照逐字一致，也未尝试恢复或清理这些文件。完整清单仅留在本机 `maps-verification-after-bpm.json`。测试写入限定在独立 `artifacts/test-maps/<token>`；真实曲目的 Worker 探测页只提供视频读取，没有写入接口。

## 2026-10-24：キスキツネ 的2780ms误填与通用拒绝检查

用户指出《キスキツネ》填入2780ms，而合理网格只需接近零的小幅调整；开头的“咚”是SE，不是第一排。用户尚未确认精确人工起点，不能把0ms或最早发声时间写成答案。

复现并区分两件事：前60秒的速度检测支持约148 BPM，没有检测到变速证据；但旧起点估计对同一份实际立体声音频，分析8秒返回1175ms，16／30／60秒返回2780ms，内部phase prominence均可到1。**这个1反映周期相位突出，不是小节起点正确率。** 原算法取全段最强相位上最早超过全局响度门槛的冲击，并允许随后12拍任意4拍支持；它既不识别SE，也没有确定小节编号。不能直接断言2780ms本身就是开头的那声SE，已证实的是起点随观察范围移动，且没有小节第一拍依据。

本次修改是通用的防误填，不是曲名特判或新完成的强拍模型：

- `analyzeFirstBeat`在同一份已解码包络上比较8／16／30秒前缀与完整片段。绝对起点相差超过半拍就拒绝；比较保留整数拍／整小节差异，不能用模一拍后的相位一致掩盖错排。
- 检查候选后紧邻4拍至少有2拍支持，防止“SE偶然落在后续网格上，隔了一段空白后有音乐”也通过原来的任意4／12拍门槛。这不是声音语义分类，稀疏前奏也可能因此被保守拒绝。
- `estimateFirstBeat`统一调用上述检查，因此工作台检测、正式Fitness生成及离线研究生成均生效，不留下另一条自动写入2780ms的入口。歧义时Worker走已有错误提示路径，不调用Offset回调；一键生成停止且不安装结果。
- 不增加解码遍数、依赖、后台常驻任务或视频画面分析。原谱音符／Offset／发布版没有回写；已经保存的2780ms不会擅自替用户改为未经确认的新值。

## 继续实现：重复pattern的小节开头

用户指出不能只做拒绝；固定BPM、通常4/4的歌曲，应当识别重复pattern里的第一重音。随后继续修改识别本体。本节是当前实现，上节的“只拦住2780ms”是中间阶段；该阶段生产结果保存在 `production-rejection-stage.json`，没有删除失败或中间记录。

`bar-pattern.ts`新增轻量的重复小节推断：

1. 使用已确认的BPM和稳定拍点相位；从同一次音频读取中按需复用现有 `MusicSpectrum`（约10帧／秒的音色与和声特征）。开头至少4秒／两小节不参与重音位置投票，避免一次SE支配结果。
2. 比较1／2／4／8小节的重复谱型，要求相似性高且优于附近的错拍间隔；不是只因整段都很响就称为重复。4/4下对应4／8／16／32拍；3/4按3／6／12／24拍比较，按钮把当前拍号传入，换拍号会取消旧任务。
3. 比较每个拍位反复出现的和声变化，至少两个独立12秒片段支持同一小节位置，并有足够的突出度，才据此选择小节开头。单次更响的军鼓／人声不直接决定第一拍。这是重音排列、谱型重复与和声接续的启发式联合证据，不是声音语义分类器。
4. 向前推算同一小节位置，选择最早有支持的发生；若前一个小节边界仅落在视频零点前80ms以内，按现有非负锚点数据格式取0，同时返回截断残差 `edgeSnapMs`。这不是宣称相位误差为0。
5. 对“后段变响导致门槛跳过安静开头”，若候选仍是同一拍点相位，而且最早的三个连续小节长度的节奏组形状相关度都高于0.82，恢复最早重复组，而非一律拒绝。孤立SE／只有一个冲击不会满足整组相似。无足够重复证据时保留原一致性与孤立开头检查。

工作台检测Worker及正式Fitness Worker都已接入。后者只额外提取游玩起点后最多60秒的频谱；不再读取第二遍音频，检测完释放，无新增依赖或游玩常驻任务。按钮成功提示区分重复乐句／重复节奏推算的候选，仍要求试听确认；不移动已写音符或视频偏移。

实际离线60秒数据：キスキツネ识别到16拍重复谱型，相似度约0.854、两个独立片段支持同一小节位置。回推边界约为-58ms，得到非负候选0ms；2780ms不再作为开头。Lovely Cavity由1610ms改为2410ms，接近人工2387ms；Happy100ms、Scream990ms保留，Sugar535ms保留原候选。原谱的正确毫秒值仍应由用户试听确认，未根据用户描述直接回写地图。

另发现浏览器原生AAC解码的合成Fitness片段会在0ms／385ms间产生候选差异；简单一致性拒绝会误伤有效重复开头，导致生成用例失败。加入三个完整节奏组的形状验证后，恢复0ms，完整生成／保存／拒绝覆盖／取消用例通过。保留此失败原因，未通过修改成功断言掩盖问题。

新增真实曲目60秒的压缩起音／频谱特征回归（约29KiB压缩数据，不含原始音频），验证从重复pattern恢复近零开头；合成3/4与4/4均验证能排除恰好同相位的SE，常量音色／不足时长不会凭空生成小节判断。284项单测与类型检查通过，4项BPM／第一拍及1项完整Fitness浏览器流程通过。正式生产Worker复核与构建信息见同目录后续 `production-comparison.json`。

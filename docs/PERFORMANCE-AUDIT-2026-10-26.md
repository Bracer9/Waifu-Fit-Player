# 游戏性能与重构调查

日期：2026-10-26。对象为当前 Windows 工作区 `sol61 @ c3100c2` 加已有未提交修改，包括新的 ended 保护。用户反馈为游玩中偶发轻微掉帧，可能与密集段有关；提前曲终故障单独处理。

优化空间存在，当前最有价值的线索在绘制／GPU 栅格提交链路，以及持续的样式与布局工作。一次 41.6ms 帧间隔与 GPU 进程约 48.9ms 的栅格提交任务重叠；相反，仅减少谱面扫描和静态 Glyph 重渲染的候选没有证实整体收益。App／Editor 的大规模拆分不应作为改善帧率的前置条件。保持现有视频、谱面、动作提示、特效和真实媒体时钟是优化约束。

## 实测结果

正常采样捕获了偶发较长帧间隔，但没有复现持续低帧率。相同 Sunlight 中段再次测量时，最长间隔从 50ms 降到 25ms，说明单次最大值波动明显。不能凭一次较顺畅的运行宣布修复，也不能仅凭音符总数确定根因。

| 曲目与版本             | 视频区间  | RAF P99.9／最大 ms | 同一 TAP 位置变化最大间隔 ms | 视频丢弃／总帧 |
| ---------------------- | --------- | ------------------ | ---------------------------- | -------------- |
| 寄明月 原版 60         | 25～55s   | 25.1／41.7         | 41.6                         | 8／1801        |
| Sunlight 原版初测 60   | 170～200s | 24.9／50.0         | 50.0                         | 6／1800        |
| Sunlight 原版对照 A 60 | 170～200s | 16.7／25.0         | 33.2                         | 10／1801       |
| Sunlight 候选 A 60     | 170～200s | 25.1／33.4         | 41.7                         | 9／1799        |
| Sunlight 候选 B 60     | 170～200s | 16.8／33.3         | 33.3                         | 7／1800        |
| Sunlight 原版对照 B 60 | 170～200s | 16.7／25.0         | 25.0                         | 7／1800        |
| Sunlight 原版 120      | 170～200s | 33.4／42.0         | 50.0                         | 2／1799        |

上述均为 30 秒样本，无 50ms 以上主线程 Long Task。Sunlight 初测出现一个约 56.4ms 的 LoAF，报告中的 scripts 为空；这不证明完全没有脚本影响，但没有提供一个对应的长 JavaScript 函数作为解释。普通 60 档的 TAP 位置变化中位数约 16.7ms，浏览器 RAF 中位数约 8.3ms。

两首歌均确认 `D3D11VideoDecoder` 硬件解码，未出现 waiting／stalled／媒体错误。计时区间没有新加载特效图片或字体；请求主要是约每 5～6 秒的 Fit Log 保存，以及寄明月的一次正常视频 Range 读取。没有证据支持通过“把所有素材再预热一遍”解决这批停顿。

### 捕获到 GPU 栅格提交与帧间隔重叠

最后一段独立 CPU profile／trace 测量 Sunlight 约 175.24～187.25 秒。在歌曲约 181.06 秒、测量开始后 5.77～5.81 秒处：

- RAF 出现 41.6ms 间隔，普通快照与 TAP 位置更新也出现同量级间隔。
- 同期 GPU 进程的 `GPUTask` 从 5.765s 持续到 5.814s，历时 48.942ms，覆盖该帧间隔。
- 该任务内 `RasterDecoderImpl::DoEndRasterCHROMIUM::Flush` 历时 47.406ms。
- 同一时间范围内，最长 renderer 主线程 RunTask 约 5.71ms，FunctionCall 约 1.58ms，未见一个对应的几十毫秒 JavaScript 任务。
- 当时采样有 6 个 TAP、2 个 HOLD，其中 1 个正在保持、2 个命中特效，没有 SPECIAL。不能由这一点推导“所有密集段必然掉帧”。

这支持优先调查栅格绘制／GPU 提交造成的阻塞，而非把这次停顿解释成全谱数组筛选或某个超长 JS 函数。**它还没有定位到具体 DOM 图层、SVG 滤镜或驱动内部原因。** GPU 进程事件的历时也不等于硬件 GPU 的纯执行耗时；trace 本身有观测开销，须与普通样本分开。

同一 12 秒窗口，CDP 累计 ScriptDuration 约 1.190s、RecalcStyleDuration 约 1.294s、LayoutDuration 约 0.582s。样式与布局合计约 1.876s，高于脚本时间，支持把渲染更新范围列为下一轮重点。CPU 采样看见 React DOM、Player 和 ribbonGeometry 的工作，但没有依据把路径计算宣称为主导瓶颈。证据为 `sunlight-profile-clean-trace.json`、对应 profile／analysis，以及 `frame-correlation.json`。

图片已 decode、没有新的网络请求，不代表 GPU 上传或所有首次绘制工作都已完成。现有预绘的两次 RAF 是提供绘制机会，不是 GPU 完成栅栏；历史增加预绘样本没有解决旧停顿，不能继续无界增加预热。

### 小范围重构候选没有证实整体收益

候选只对 `NoteGlyph`／`LaneGlyph` 使用 memo，并把原有逐轨全谱筛选改为先按轨道分组。没有改音符位置公式、HOLD 几何、图层、时钟、素材、帧率或特效。测试顺序为原版 A、候选 A、候选 B、原版 B，各用新的浏览器上下文。

| 30 秒内累计时间        | 原版 A | 候选 A | 候选 B | 原版 B |
| ---------------------- | -----: | -----: | -----: | -----: |
| 主线程 TaskDuration 秒 |  9.255 | 10.394 | 10.231 | 10.657 |
| ScriptDuration 秒      |  2.600 |  2.731 |  2.644 |  2.972 |
| RecalcStyleDuration 秒 |  2.269 |  2.626 |  2.595 |  2.629 |
| LayoutDuration 秒      |  1.200 |  1.389 |  1.397 |  1.401 |

同类两次平均，候选 ScriptDuration 约低 3.5%，TaskDuration 反而约高 3.6%。每类只有两次、原版本身有波动，因此不把这些差值解释成稳定收益或稳定退化。可以确定的是：这个候选没有展示足以解释或解决偶发掉帧的整体改善，不应仅凭静态代码分析直接交付为性能修复。

在 Sunlight 的 176、181、185、195 秒暂停位置，候选与原版的轨道节点数量、SVG 路径、位置样式、viewBox、动作／图标／帧号和无障碍标签完全一致。截图也保留原场景；这是已覆盖状态的输出核对，不是全部谱面和设备的视觉验收。

上述累计时间只覆盖中段测量窗口，数据导出放在计时结束后。TaskDuration 包含多类工作，不能与 Script／Layout／Style 再次相加，也不能称为整台机器 CPU 占用率。两段最初基线在读指标前导出了原始数据，边界额外约 0.43～0.45 秒，所以只用其帧／视频样本，不把它们的 TaskDuration 用于这个对照。

### 120Hz 提高运动更新频率 也增加持续成本

120 档 TAP 位置变化间隔中位数从约 16.7ms 降到 8.3ms，但 P95 仍约 16.6ms，最大间隔 50ms。该段 30 秒内 TaskDuration 为 16.847s，较 60 档原版两次平均 9.956s 高约 69%；样式计算为 4.867s，60 档平均约 2.449s。视频丢帧较少，不代表音符更新已无停顿。

120 档可改善连续移动的细腻程度，但本轮不能把它作为偶发卡顿的修复，也不据此更改用户帧率偏好。测试 RAF 平均约 111Hz、常见间隔 8.3ms，未达到稳定每秒 120 次回调，更不是系统标称的 165Hz。

## 当前结构与开销

### 每帧更新集中在 Player

[MediaController](../src/media.ts) 用一个 RAF 循环读取实际 `video.currentTime`，普通时间约 60Hz，Player 可选择 60／120／display。App 订阅媒体状态，没有订阅每帧时间；不能把 App 文件较大描述成“整个应用每帧重渲染”。BPM、热量／连击和 Transport 各自订阅普通时间。

[Player](../src/views/Player.tsx) 已把 ARMS 合并、音符排序、长条连接和节拍索引放在 `useMemo` 中，但每帧仍为五条轨道分别扫描完整显示音符数组，筛选可见音符和释放特效。仅这两部分约为每帧 `10 × 显示音符数` 次谓词调用，另有可见集的筛选／映射。按轨道预分组可把这部分降至约 `2 × 显示音符数`，不改变任何显示规则。这是减少工作量的机会，不等于已经证明这些循环导致几十毫秒卡顿。

当前发布版《寄明月》有 162 个原始音符／58 个 HOLD，Sunlight 有 486 个／118 个 HOLD。这里是原始谱面事件数，ARMS 合并后的显示数会不同。同屏数量、HOLD 覆盖长度与特效重叠，比整首音符总量更接近绘制负担。

`NoteGlyph` 和 `LaneGlyph` 的属性大多不随时间改变，但目前会随 Player 再次执行、生成 SVG 元素。对这些纯静态部分使用 `memo`，可以保留移动外壳更新并跳过相同图形的重复协调。只给每帧都改变属性的整个 Player／HoldRibbon 套 `memo`，通常不能解决这个问题。

### 长条同时涉及几何 路径提交 布局和绘制

[HoldRibbon](../src/components/HoldRibbon.tsx) 和 [ribbonGeometry](../src/ribbonGeometry.ts) 已经限制屏外生成范围，并按 6px 网格保持原始波浪相位。之前导致首次停顿的实时 SVG blur 已被多层透明矢量描边替代，不能再次把“删除实时模糊”列为尚未实施的优化。

当前仍有这些工作：

- HOLD 的外壳每帧更新 `left`／`width`；SVG 的可见范围、滤镜边界也会改变。进入保持阶段后，路径随截取范围变化。
- 路径由采样点和三次曲线字符串生成，同一个轮廓用于 bloom、4 层 glow、aura 和 color，共 7 个 path。
- 白边保留 `feMorphology`，普通音符与部分提示保留 drop-shadow。滤镜仍有成本，但存在滤镜不等于它就是偶发长帧的原因。
- 轨道上的继承 CSS 变量控制命中与持续反馈，变量变化还可能触发子树样式工作。

后续可单独验证：把纯平移从 `left` 更新拆出、缩小动态变量作用范围、把不变的几何部分与活动端裁切分开。移动属性通常优先考虑 transform；涉及 width、SVG path、滤镜时仍须检查真实绘制结果，不能保证一个 transform 就消除布局／重绘。[浏览器动画性能指南](https://web.dev/articles/animations-guide)

必须保留波浪相位、提示大小、白边、柔光、时间连接、后音符覆盖前音符的顺序及判定线裁切。整体缩放长条会改变波浪或描边；预生成无边界整条 SVG 会重新引入超长 HOLD 的巨大表面，这两种方式不符合当前约束。

### HUD 的刷新边界可以缩小

[PracticeArtwork](../src/components/PracticeArtwork.tsx) 中的 BPM、连击与热量每次普通时间通知都会重新执行，即使最终数字不变。连击和热量已经使用索引查询，不必重新设计计数算法。

可以为显示值建立派生快照：BPM 数字、整数连击、保留一位小数的热量不变时，快照保持相同，让 React 跳过组件更新。仍在现有媒体通知时刻重新判断，值变化立即反映，不采用会延迟反馈的粗粒度定时器。`useSyncExternalStore` 按 `Object.is` 比较快照；返回每次新建的对象会破坏这一用途。[React 官方说明](https://react.dev/reference/react/useSyncExternalStore)

[Transport](../src/components/Transport.tsx) 可把动态进度条与静态播放／音量按钮、秒级文字分开。进度条保持流畅，减少的是无变化部分的工作。

## 资源使用

资源盘点脚本仅读取文件大小及 PNG 头，未进行全图解码。像素容量估算不等于 Chrome 实际内存或显存使用。

| 资源             | 文件或像素规模                                      | 判断                                                                                          |
| ---------------- | --------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 普通命中配色图集 | 5 张，每张 2048×1536；RGBA 约 12 MiB，合计约 60 MiB | 已按谱面使用的配色准备；不是每次都强制加载全部配色。                                          |
| SPECIAL burst    | 每张 3200×770；RGBA 约 9.4 MiB                      | 按该谱面的 SPECIAL 图案准备。                                                                 |
| 舞台背景 v6      | 1672×941；文件约 1.92 MiB，RGBA 约 6.0 MiB          | 固定资源，准备后复用。                                                                        |
| 16 个菜单 SE     | WAV 文件合计约 759 KiB                              | 初始化预加载，规模较小；没有证据支持优先改为新的音频系统。                                    |
| 现有主 JS 包     | 605616 字节；本地 gzip 估算 202845 字节             | 包含工作台等代码；延迟加载可能改善启动，不直接等于中段帧率改善。gzip 数不是实测 HTTP 传输量。 |
| 现有主 CSS 包    | 201464 字节                                         | 拆包应与样式影响范围分别评估，不能仅按文件大小判断运行成本。                                  |

[asset-cache](../src/asset-cache.ts) 共享加载任务和成功结果，失败会移除、允许重试。固定游戏特效资源数量有限；[useBriefingMotion](../src/useBriefingMotion.ts) 还会把所选曲绘加入同一缓存，成功项没有容量淘汰。长时间访问不同曲绘或替换封面可能增加保留对象，应通过同一上下文的长时间换曲验证实际增长。不能把多个全新测试上下文的短测当作已经排除泄漏。

如果后续增加缓存预算，应将当前游戏资源固定保留，菜单曲绘按最近使用情况管理，并在离开相应场景后释放不再需要的引用。随意清空全部缓存可能把图片解码／上传重新带入下一次游玩。

无损重新编码 PNG 可以节省文件字节，但尺寸不变时不会相同比例减少解码像素容量；降低分辨率、减少动画帧、合并配色或改实时着色，需要额外证明视觉与性能收益。本轮没有降低素材质量。

菜单 BGM 保留当前压缩音轨 Blob，换轨时撤销旧对象 URL。进入游玩后，菜单 Audio 停止，相关 AudioContext 会在无菜单音频需求时 suspend；MusicPulse 在游玩场景卸载。分析 Worker 只在请求分析时启动。它们不是本轮证据支持的持续游玩负担。

视频采用同一个 video 和本地 Range 流式服务，不会为整首视频预解码。Fit Log 每秒累计、约每 5 秒持久化；服务端读写完整记录文件，当前文件约 13 KiB，属长期扩展性观察点。不能仅因一次长帧与写入时间接近就判定是磁盘保存造成卡顿。

public 中 v2～v5 舞台背景合计约 7.0 MiB，会随默认构建复制。清理发行目录的历史素材可以缩小交付体积；没有被页面请求的旧文件不会直接造成游戏掉帧。源素材是否保留应与发行打包规则分开处理。

## 重构范围与顺序

| 顺序 | 工作                                                                             | 对体验的约束与验证                                                       |
| ---- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 1    | 关联长 GPU 栅格任务与具体绘制图层；单因素验证 HOLD、提示滤镜及命中图集更新的成本 | 先用隔离诊断定位，正式方案保留所有视觉；不能把临时关闭特效当作交付。     |
| 2    | 缩小样式更新范围，拆分 HOLD 的移动、裁切和固定图形；为 HUD 建立显示值快照        | 保持所有长条语义与反馈时刻，覆盖超长 HOLD、连接、SWAY、流速变化及 seek。 |
| 3    | 曲绘缓存预算与发行素材管理                                                       | 以连续换歌的实际内存增长为依据；不在活动游玩过程中回收正在使用的资源。   |
| 4    | App 的作品加载／保存协调与游玩流程拆分；Editor 按工具／交互拆分                  | 为可维护性降低状态耦合，单独提交与验证，不承诺仅拆文件就提升 FPS。       |

按轨道分组和静态 Glyph memo 可以成为整理渲染数据的一部分，但本轮对照不支持将其单独列为已经有效的掉帧修复。优先级应服从时间线与重复实测，而不是代码看起来“可以更快”。

App 约 2144 行、Editor 约 2172 行，继续扩展时值得提取清晰的流程边界。适合先拆纯查询／渲染数据，再处理状态协调。提前曲终保护涉及播放状态和媒体复用，应保留现有测试，避免与一次广泛重构混在一起。

当前证据不支持更换 React、迁移 Canvas／WebGL、全量引入对象池、把小型谱面计算送到 Worker，或全局强制 GPU 图层。它们都可能增加复杂度或资源开销，应在较小修改不能满足目标时再评估。

任何索引或渲染重构都须保留：实际视频时间、videoOffset、发布游玩区间、暂停／任意方向 seek／重开、1ms 连接容差、同轨重叠优先级、ARMS 配对和 SPECIAL 重叠。只按开始时间二分、只维护前进游标，可能漏掉跨越查询时刻的长条或无法回拖。

## 采样方法与验收边界

用户停止游玩后运行独立有窗口 Chrome，GPU 开启，内容视口 2560×1440、DPR 1、流速 5。系统显示器标称 165Hz，测试窗口 RAF 实测约 120Hz；本轮不能声称完成原生 165Hz 或 M3 真机验证。

使用当前源码直接调用 Vite 构建到忽略的 artifacts 子目录，避开 npm prebuild 和用户 dist；复制两首真实曲目到独立 maps，保留视频时间戳，不使用真实 Fit Log。测试端口 4184。样本从正常选曲／准备／倒计时进入，随后暂停 seek 到目标段前 2 秒，恢复后测中段，因此它们主要回答稳定游玩问题，不能替代整首自然播放或首次效果出现的测试。

记录 RAF、相同 TAP 的 transform 变化、普通媒体快照、视频丢帧差值、Long Task／LoAF、资源请求、低频 DOM 数量和 CDP 指标。RAF 不是实际屏幕呈现次数，TAP 位置样本不是全部 HOLD 的逐帧证明。视频帧回调的 processingDuration 也不能直接当作每帧串行 CPU 解码耗时。

正常性能样本不启用截图 trace，截图均在暂停后取得。CPU profile／trace 单独采样。对照版仅存在于 artifacts，并未应用到正式源码。

现有性能回归主要覆盖 7～8 秒场景，P95 帧间隔小于 34ms、视频丢帧率小于 8% 等阈值可以防明显退化，但不足以发现低频轻微卡顿。50ms 长任务阈值也会漏掉超过高刷新率预算的工作。[Chrome 对 Long Task 与 LoAF 的说明](https://developer.chrome.com/docs/web-platform/long-animation-frames)

后续验收应分别观察脚本、样式／布局、RAF 长间隔、音符位置长间隔和视频丢帧；保留 P99.9、最大值与时间点，用相同真实曲段重复比较。常规 CI 不宜只用一次最大值硬判失败，完整长曲、连续重开／换歌和目标设备的实际体验也要覆盖。
